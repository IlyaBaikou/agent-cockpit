# Архитектура Agent Hub

Состояние кода: **0.2.13**, пилот. Документ для коллег, которые хотят исправить дефект, добавить функцию или подключить нового исполнителя. Описывает реализованное поведение, а не корпоративную целевую архитектуру.

## 1. Что это за система

Agent Hub — общий чат сотрудников с локальными агентами. Сотрудник подключает несколько именованных агентов, выбирает для каждого CLI и рабочую папку. Люди общаются в спейсах и каналах; агентские обсуждения идут в тредах. Упоминание человека создаёт уведомление. Упоминание агента создаёт запрос работы, иногда требующий согласования владельца.

Координатор хранит переписку, доступы, очередь, разрешения и отметки прочтения. **Он не запускает модели и не получает локальную рабочую папку целиком.** CLI запускается на компьютере владельца, читает разрешённые локальные материалы и отправляет ответ в тред. Текст запроса, прочитанные агентом материалы и ответ обрабатываются выбранным провайдером; опубликованный ответ виден участникам спейса.

```text
Компьютер сотрудника A                         Компьютер сотрудника B
┌─────────────────────────┐                   ┌─────────────────────────┐
│ Electron UI → IPC       │                   │ Electron UI → IPC       │
│ Main → EmployeeRunner   │                   │ Main → EmployeeRunner   │
│          ↓              │                   │          ↓              │
│ Codex / Claude / Cursor │                   │ Codex / Claude / Cursor │
│ Локальные папки и tools │                   │ Локальные папки и tools │
└───────────┬─────────────┘                   └───────────┬─────────────┘
            └──── HTTPS POST /v2/rpc + GET /v2/events (SSE) ────┘
                              ↓
                CollaborationService → PostgreSQL
```

В локальном демо тот же сервис запускается внутри Electron на `127.0.0.1` со SQLite. Облачный вариант использует PostgreSQL и подходит для теста без VPN. Это не P2P и не автономный серверный агент: закрытие приложения через Quit останавливает его раннеры. Закрытие окна оставляет приложение в трее.

## 3. Модель данных

```text
Employee ── владеет ── Agent (executor, device, enabled, allowWrite, primary, fallback)
    │
    └── член Space ── Channel ── чат канала (Message.thread = null)
                         └────── Thread ── Message / Job / Participation

Employee + Channel + Thread|null ── ReadPosition
Employee ── Notice (собственный inbox, read flag)
```

- Все каналы наследуют состав спейса, отдельных channel ACL пока нет.
- Только создатель спейса меняет участников и выдаёт его общие приглашения. Создатель канала либо владелец спейса управляет каналом.
- `Agent` принадлежит одному сотруднику и устройству. Один агент сотрудника считается `primary`: его автоматически выбирают входящие обращения коллег и peer-агентов. Первый legacy-агент служит детерминированным default до явного переключения. Рабочая папка и путь CLI хранятся на desktop, не в публичном профиле агента.
- `Thread.revision` меняется при человеческих сообщениях/управлении тредом. Это граница актуальности запроса, не номер сообщения.
- `Job` содержит режим, инициатора, lease, бюджет цепочки, статус и выданную сервером `authorization`.
- `Participation` хранит одно текущее разрешение на пару **тред + агент**: статус, остаток, накопленный расход, revision и ожидающий запрос с source message.
- `Message.seq` — монотонный номер сообщения, отдельный от `Notice.seq`. Не сравнивайте время `createdAt` для прочтения: возможны одинаковые timestamps.
- `Notice.read` — прочтение уведомления. Это **не** одобрение агента и **не** отметка прочтения всего треда.

Спейс хранит историю централизованно; у desktop есть текущий снимок и локальные настройки, а не независимая копия истины. Снимки отфильтрованы по членству, каналам и правам на диагностику. Каталог сотрудников/агентов в пилоте глобальный; это не полноценная directory privacy model.

## 4. Отправка, очередь и выполнение

1. Renderer создаёт `requestId`, сразу показывает сообщение со статусом отправки и освобождает поле ввода. Outbox и черновики находятся в памяти процесса, не переживают Quit.
   Пока `outbox` содержит `sending` для текущих employee/hub/space/channel/thread, кнопка показывает «Отправляется…». Защита есть также в submit/retry, а не только через `disabled`: повторный клик, программный submit и Ctrl/Cmd+Enter не отправляют следующий черновик до подтверждения/ошибки. Получение сообщения через sync тоже считается подтверждением. Поле ввода остаётся доступным; блокировка не распространяется на другие чаты.
2. Main проверяет IPC sender и allowlist, отправляет `post` координатору.
3. Сервис проверяет членство, канал, адресата и повторную доставку. Упоминание агента из чата создаёт тред; в канале видна одна карточка этого треда.
4. `route()` либо ставит **авторизованное** задание в очередь, либо создаёт ожидающее согласование без задания и без вызова модели.
5. Локальный `EmployeeRunner` опрашивает очередь примерно раз в 5 секунд, сообщает health, атомарно забирает задание через `claim`.
6. Раннер готовит контекст, при необходимости делает один summary pass, проверяет lease/revision и вызывает выбранный CLI. Write работает в отдельном worktree.
7. `complete` публикует ответ. `addressing.ts` согласует видимые упоминания с последней строкой `ROUTE: agent:<ID>`, `human:<ID>`, `done` или `unable`. Текст не выдаёт прав доступа.

### Мгновенные обновления и статус набора

- Сообщения и все мутации по-прежнему отправляются подтверждаемым `POST /v2/rpc`. После успешной мутации процесс координатора посылает подключённым desktop-клиентам SSE-сигнал `change` без текста сообщения; каждый клиент сразу вызывает обычный `sync` и получает только разрешённый ему снимок. После обновления main будит локальные раннеры, поэтому новый агентский запрос не ждёт их резервного пятисекундного poll.
- Каждый desktop держит одно исходящее `GET /v2/events` соединение с координатором. Это не P2P и не открытый порт на ноутбуке. При обрыве клиент переподключается с задержкой 0,5–5 секунд; редкий 30-секундный `sync` остаётся страховкой от пропущенного события.
- Человеческий статус набора отправляется через `POST /v2/typing` и распространяется SSE-событием только участникам спейса. Он содержит employee/context/expiry, живёт в памяти процесса до 5 секунд, не попадает в PostgreSQL, историю или запрос модели. Агентскую работу уже показывает состояние `Job`, отдельный «агент печатает» не создаётся.
- Текущий Railway-пилот должен работать в **одном экземпляре coordinator**: список SSE-подписчиков и typing-присутствие локальны процессу. Перед несколькими репликами нужен общий event bus — например, PostgreSQL `LISTEN/NOTIFY` для invalidation и Redis/NATS для presence — плюс тесты межрепличной доставки. Обычные RPC/данные остаются транзакционными в PostgreSQL.

### Упоминания и передача ответа

- Канонический адрес сотрудника — `@{u:ID}`, фактически выбранного default-агента — `@{a:ID}`. Renderer автоматически сопоставляет отдельный пункт «агент сотрудника» с текущим `primary`; prompt публикует по одному default peer на владельца. Владелец видит все собственные агенты и может явно вызвать вспомогательного. Простые `@имена` не угадываются: имена могут совпадать.
- Хаб добавляет видимый тег адресата из `ROUTE`, если модель его пропустила. Итоговый ответ адресуется инициатору текущей цепочки (`Job.requestedBy`), запрос решения — указанному сотруднику, передача — указанному агенту.
- Без `ROUTE` одно уникальное упоминание агента вызывает его в **том же треде** через обычный `route()` и participation gate. Повтор одного тега не дублирует запуск. Одно человеческое упоминание без маршрута переводит тред в ожидание этого сотрудника; его агенты не запускаются.
- Несколько разных агентов, самовызов, недоступный адресат или конфликт упоминания с `ROUTE` сохраняют ответ, но останавливают передачу с ошибкой. В частности, `@{a:ID}` вместе с `ROUTE: done` — конфликт. Для справочного упоминания пишите имя без `@`.
- Кодовые блоки (в том числе незакрытые), inline code, цитаты, отступы кода, Markdown-ссылки и URL не считаются вызовами. Это правило применяется также к сообщениям людей.
- Вмешательство человека во время работы по-прежнему останавливает автоматическую передачу. Лимит цепочки, согласования, запрет автоматических write и идемпотентность `complete` остаются действующими.
- Человеческое упоминание создаёт уведомление даже без подписки на тред. При запросе решения оно имеет заголовок «Нужно ваше решение». Уведомления об ответе, упоминании, подписке и завершении дедуплицируются по `Notice.event = Message.id` + employee. Отдельные ошибки/запросы согласования остаются отдельными событиями. Mute, прочтение и настройки системных уведомлений не обходятся.
- Нажатие на тег добавляет адресата в редактор ответа, **не отправляет** сообщение и не запускает модель. Старые сообщения не переписываются и не переигрываются.
- В списке адресатов ↑/↓ меняют подсвеченный вариант, Enter вставляет тег и немедленно закрывает список. Ctrl/Cmd+Enter при открытом списке также только выбирает адресата. Esc, Tab, уход фокуса и клик снаружи закрывают список без вставки. Индекс сбрасывается при фильтрации; пустая выдача и ввод через IME не отправляют сообщения.
- Порядок адресатов: другие сотрудники текущего спейса → по одному default-агенту каждого коллеги → собственные включённые агенты, начиная с default. Вспомогательные агенты коллег не выдаются как отдельный выбор; настроенный fallback включается хабом при ошибке основного. Свой профиль исключается по ID, а не имени (тёзки остаются). Собственные агенты доступны и в одиночном спейсе. Старые упоминания самого себя остаются читаемыми, но не предлагают вставить тег себя в ответ; серверные права и уведомления от чужих упоминаний не меняются.

Очередь ждёт раннер до двух минут. Lease работающего задания — 90 секунд с продлением; потеря связи приводит к остановке/ошибке, а не к обещанию «ничего не выполнено». На тред одновременно допускается одно активное задание; на агента — одно running-задание. Цепочка ограничена 12 ответами независимо от персональных разрешений.

Сервис хранит до 2 000 idempotency-ответов. Для `post` дополнительный `Message.clientRequestId` переживает вытеснение этого cache: потерянный ack не создаёт повторный тред/запуск. Повторная доставка `complete` не запускает CLI заново. После возможного выполнения write автоматического повторного запуска нет; частичные изменения остаются владельцу.

## 5. Согласование и расход запусков

Правило по умолчанию: **участники могут попросить вашего агента, но не могут сами разрешить его запуск**.

| Источник запуска | Что разрешено |
| --- | --- |
| Владелец сам отправил `@свой агент` | Один явный запуск. Не пополняет разрешение на автоматический диалог. |
| Коллега вызвал агента | Нужен остаток разрешения на этот тред/агента; иначе pending. |
| Агент передал вопрос, в том числе обратно агенту инициатора | То же правило; исходный `requestedBy` не считается новым апрувом. |
| Настроенный резервный агент | Отдельное разрешение именно резервному агенту. Основной его не наследует. |
| Write/fix | Явный запрос владельца в режиме write **или** кнопка «Действуй» под актуальным read-ответом своего агента + локальное allowWrite. Апрув участия даёт только read. |

Владелец видит вопрос, инициатора и, при передаче, агента-отправителя. Доступны **один ответ**, **обсуждение на 3 запуска**, **отклонить**. При исчерпании — новое ограниченное продление. Разрешение относится к участию в этом треде, а не только к одной фразе; сервис не пытается моделью угадывать, сменилась ли тема. Обсуждайте разные задачи в разных тредах.

**Единица лимита — задача, резервируемая при постановке в очередь.** Ошибки, отмены и таймаут очереди не возвращают резерв. У задачи может быть основной CLI-вызов и дополнительный вызов сжатия контекста. Это намеренно консервативный контроль запусков, а не измеритель/потолок токенов или стоимости. До апрува нет ни основного, ни summary-вызова; периодические CLI health checks не являются обсуждением с моделью.

Защиты реализованы на координаторе, не только кнопками UI:

- Только аутентифицированный владелец агента может принять решение; владелец спейса не получает этого права за коллегу.
- «Действуй» доступно только под последним read-ответом собственного агента. Сервер повторно проверяет владельца, `allowWrite`, отсутствие активной работы и `Thread.revision`, затем одной транзакцией добавляет явную команду человека и создаёт write-задание. `requestId` делает двойной клик идемпотентным. Старый или чужой ответ не является разрешением.
- Решение несёт `Participation.revision` и `Thread.revision`. Устаревшее решение отклоняется; нужно прочитать новое состояние и повторить.
- Разрешены только размеры 1 и 3. Выдача разрешения, списание первого резерва и создание Job — одна транзакция.
- Повторные упоминания обновляют ожидающий вопрос, но не обнуляют расход и не обходят отказ. Повторное уведомление о том же ожидающем запросе не создаётся.
- Новый явный адресат заменяет старый ожидающий переход; не обнуляет уже выданные бюджеты других агентов.
- `claim` повторно проверяет полномочия. CLI не получает контекст ожидающего pending-запроса через очередь.
- Stop, завершение (включая `ROUTE: done`), архив канала и сохранение настроек агента отзывают соответствующие разрешения. Удаление участника консервативно отзывает разрешения во всём спейсе. Повторное открытие ничего не восстанавливает автоматически.
- Отзыв прекращает авторизованные по нему queued/running задания. Запоздалый ответ не может запустить новый цикл. Уже переданные провайдеру данные отозвать нельзя.
- Автоматический write fallback не допускается даже до начала выполнения: владельцу нужен отдельный write-запрос резервному агенту.

Отклонённый запрос остаётся видимым; владелец может передумать через карточку. Чтение карточки/уведомления, обычное сообщение «согласен» и summary сами по себе ничего не разрешают. Владельцу доступна кнопка «Отозвать и остановить» для выданного разрешения. Для остановки любого текущего задания служит также общий Stop треда.

## 6. Непрочитанное, уведомления и позиция истории

Баджи считают чужие человеческие сообщения и ответы агентов. Системные записи и собственные человеческие сообщения в число не входят. Бадж спейса — сумма его каналов, бадж канала — чат канала плюс вложенные треды. Одно сообщение не учитывается дважды внутри одного суммарного счётчика.

`ReadPosition` принадлежит сотруднику и точному месту `channel + thread|null`. UI посылает ID последнего показанного сообщения через `read`; сервер проверяет доступ и принадлежность сообщения, двигает курсор только вперёд. Поэтому открытие канала не читает его треды, а запоздавший сетевой ответ не помечает новым курсором ещё не увиденные сообщения.

Прочтение происходит в активном видимом окне, без перекрывающего диалога, когда история открыта у конца. Свёрнутое/неактивное окно и чтение старой части истории не снимают новые баджи. При входе в тред UI устанавливает позицию конца **до отрисовки**, без smooth-scroll. Обновления сохраняют позицию читателя, если он ушёл от конца.

Счётчик «Уведомления» показывает только непрочитанные Notice. Открытие чата/треда у конца помечает прочитанными его уведомления до номера, полученного в снимке UI. В inbox новые показаны отдельно, прочитанные — в сворачиваемой группе. Кнопки:

- «Отметить все прочитанными» меняет только собственные уведомления до увиденного номера, не курсоры сообщений и не апрувы.
- «Очистить прочитанные» удаляет только собственные прочитанные уведомления до увиденного номера; история, задания, чужие уведомления и новые arrivals сохраняются.

Notice sequence никогда не уменьшается при очистке. Desktop хранит отдельный cursor доставки OS-баннеров: очистка inbox не должна вызывать их повторный показ. Уже прочитанные уведомления не показываются повторно через `pendingNotices`. Удаление уже показанного баннера из системного центра уведомлений ОС отдельно не реализовано. Мьют канала подавляет баннеры, но не историю, баджи или доступ к inbox. Само наличие новых сообщений не должно открывать окно; `show/focus` вызываются явным открытием приложения, кликом по уведомлению/трею и обработкой second-instance.

## 7. Контекст и адаптеры

Подробности — [CONTEXT.md](docs/CONTEXT.md). На основной вызов идут стабильные инструкции, каталог участников, валидированный слепок, последние сообщения и ссылки на оригиналы. Большие блоки кода не повторяются целиком при каждой реплике. Архив треда создаётся во временной локальной папке и удаляется после выполнения; crash может оставить временные файлы.

Источник истины — исходные сообщения и актуальные файлы, не summary. Хеши/цитаты проверяют привязку слепка к истории, но не истинность его выводов и не свежесть репозитория. Метрики в UI — символы, не счёт провайдера. Сессии между заданиями пока не переиспользуются; гарантированного cache hit нет.

Новый исполнитель подключается через контракт `AgentAdapter`, `adapterFor()` и тип `Executor`; обновите селектор UI, диагностику и тесты. `healthCheck` не должен делать платный модельный запрос. `run` обязан поддерживать отмену, корректно извлекать финальный ответ и сохранять диагностические признаки ошибок. Не принимайте tool events / initialization как итоговый ответ. Не переиспользуйте credentials другого сотрудника и не запускайте CLI на координаторе.

## 8. Границы безопасности

- Удалённые соединения — HTTPS, локальные — loopback HTTP. RPC, typing и SSE требуют Bearer; браузерный Origin запрещён. Размер v2 body ограничен 1 MB. SSE не переносит содержимое сообщения, но сам факт активности доступен аутентифицированным клиентам; typing дополнительно ограничен участниками спейса.
- Приглашения и выданные персональные токены в БД хранятся хешированными. Bootstrap-токены находятся в окружении сервера. В desktop токен зашифрован Electron safeStorage (Keychain/DPAPI).
- Renderer без Node, с sandbox/contextIsolation, CSP и allowlist IPC; сообщения, вопросы согласования и диагностика выводятся экранированными. Нельзя вставлять ответ агента как доверенный HTML или выполнять его инструкции в main.
- Права на модификацию и права на обсуждение раздельны. Git worktree не равен OS sandbox. Особенно Claude/Cursor tool policies не дают гарантии файловой изоляции; отдельно настроенные MCP-инструменты могут иметь дополнительные полномочия.
- Диагностика хранится ограниченно и доступна владельцу агента / bootstrap-оператору с доступом к спейсу. Подробности — [DIAGNOSTICS.md](docs/DIAGNOSTICS.md). Автоматическое редактирование stdout/stderr скрывает известные шаблоны, но не гарантирует удаления любой приватной информации.
- Jira/Confluence/PR ссылки — контекст. Читать их агент может только через собственные доступные инструменты. Приложение не наследует автоматически OAuth Desktop Slack/Claude/Cursor и не имеет общего MCP gateway.
- Пилот предполагает доверенных сотрудников. SSO, проверка корпоративной личности, полноценный аудит tools, центральный secret broker, корпоративная ротация и ограничения исходящего трафика ещё не реализованы.

## 9. Хранилище, миграции и совместимость

Текущее v2 состояние — один JSON-документ в `collaboration_state`, row `id=1`. PostgreSQL сериализует мутации через `SELECT ... FOR UPDATE`; SQLite использует `BEGIN IMMEDIATE`. В памяти тестов мутации происходят над копией. При исключении транзакция не сохраняет частично выданное разрешение/курсор/задание. Idle `sync` и пустой `claim` читают без переписывания документа; expiry/migration требуют транзакции.

Это простой пилот, **не масштабируемая корпоративная БД**: полные снимки без пагинации, рост JSON, линейные проходы, единая точка сериализации. Следующий масштабный шаг — нормализованные таблицы jobs/messages/grants/read cursors, индексы, инкрементальные события, ограничение очередей и retention.

0.2.7 добавляет необязательные поля без удаления переписки/credentials. Миграция:

1. Сохраняет историю, назначает сообщениям sequence по существующему порядку и baseline существующим сотрудникам. Старый архив не создаёт лавину непрочитанных; новые сообщения учитываются. Существующий inbox автоматически не очищается: можно открыть обсуждения или воспользоваться кнопками.
2. Не выдаёт разрешения из старого `enabled`. Старые **queued** задания отменяются с видимой причиной. Уже running задания могут закончиться; следующий handoff проходит новый gate.
3. Старый desktop на новом координаторе не обходит согласование, но не имеет кнопок для него. Нужно обновить все desktops.
4. Новый desktop на старом координаторе останавливает раннеры и показывает требование обновить сервер. Не откатывайте coordinator на код без participation gate ради совместимости.

При безопасном rollout дождитесь отсутствия активных заданий, сделайте штатную резервную копию PostgreSQL, обновите coordinator, затем desktops. Уже работающие задачи могут завершаться во время обновления; rollout не гарантирует отсутствия сетевого разрыва. **Откат старого кода может отключить gate**, хотя JSON-поля сохранятся. При аварии сначала остановите/отключите агентов; восстанавливайте проверенную версию и БД по операционной процедуре, не удаляйте таблицы.

## 10. Локальная разработка и проверка

Нужен Node 22.13+ либо 24 и npm. Для большинства тестов не нужны аккаунты CLI, Slack, Railway или внешний PostgreSQL.

```sh
npm ci
npm run check
node node_modules/electron/cli.js scripts/smoke-context-ui.cjs
```

`npm run check` выполняет TypeScript check, build и Vitest. UI fixture использует вымышленные данные и отдельный временный профиль; не вызывает реальные модели. PostgreSQL unit tests используют `pg-mem`, а не настоящий сетевой PostgreSQL: это не полная проверка его блокировок/производительности.

Для ручной разработки запускайте отдельный профиль, чтобы не затронуть рабочие credentials и раннеры:

```sh
npm run build
node node_modules/electron/cli.js . --profile-dir /absolute/path/to/agent-hub-dev-profile
```

Выберите «Попробовать локально». Не подключайте основной аккаунт и продуктовую папку к экспериментальному процессу. Для реального CLI smoke нужен отдельный согласованный запуск с синтетической папкой — он может расходовать подписку.

Основные регрессии:

| Изменение | Минимальные проверки |
| --- | --- |
| RPC / доступы / очередь | `collaboration`, `participation`, `channels`, `read-state` tests, включая denied/foreign/stale requests. |
| Апрувы | Повторы/потерянный ack, параллельные решения, расход после ошибки, fallback, возврат к агенту инициатора, revoke/stop/resolve, миграция. |
| UI / баджи | `smoke-context-ui.cjs`: роли, escaping, свернутое окно, соседние треды, позиция истории, новые arrivals, очистка inbox. |
| Realtime / typing | `collaboration` HTTP test: SSE auth/change/typing; `smoke-context-ui.cjs`: точный context, start/stop и исчезновение индикатора. |
| Адаптер / процессы | `agent-diagnostics`, `diagnostic-delivery`, `employee-runner`, `process-diagnostics` на нужной ОС. |
| Сжатие | `context`, `employee-runner`: originals, source hash, failed-summary backoff и отмена до вызова. |

### Как добавить новую RPC-функцию

1. Добавьте сериализуемые типы и аддитивную миграцию при необходимости. Не доверяйте отсутствующему полю как разрешению.
2. Реализуйте проверку actor/space/owner в сервисе. Побочные изменения и проверка revision должны быть в одной транзакции.
3. Для renderer добавьте только необходимую операцию в allowlist `desktop.ts`. Не пробрасывайте произвольные shell/HTTP/файловые действия через bridge.
4. Добавьте success, unauthorized, stale, duplicate и persistence tests, затем UI с escaping и pending/error состояниями.
5. Обновите этот документ, релизные заметки и явно укажите требуемые версии coordinator/desktop.

## 11. Сборка и публикация

`npm run desktop:dist` собирает DMG arm64/x64 и Windows NSIS x64 согласно `electron-builder.yml`; соответствующие ОС проверяются CI. Установщик не включает CLI, авторизацию или пользовательские рабочие папки. Профиль хранится вне каталога установки; обновление сохраняет его. Сборки пока без корпоративной подписи/notarization и auto-update.

С 0.2.9 Mac-пилот использует `mac.identity: '-'`: полноценную ad-hoc подпись bundle, без сертификата или приватного ключа. `identity: null` пропускает подпись и оставлял некорректную подпись Electron после переименования приложения; это ломало регистрацию UNNotification. CI проверяет обе архитектуры через `codesign --verify --deep --strict` и идентификатор `com.animaplay.agenthub`. Это проверка целостности, **не** Developer ID, notarization или разрешение Gatekeeper. Для доверенного корпоративного распространения нужны отдельная политика доставки и соответствующие сертификаты; не отключать защиту ОС. DMG лишь содержит приложение, которое следует перенести в `/Applications`.

`src/notification-probe.ts` ждёт события native `show` / `failed` или 20-секундного таймаута. `show` подтверждает принятие системой, но не фактический просмотр/баннер; Focus, screen sharing и разрешения ОС могут подавлять показ. UI показывает ошибку или «не подтверждено» и блокирует повторный тест на время ожидания. Тест не вызывает модель. `--smoke-test` использует отдельный временный профиль, проверяет SQLite и загрузку подписанного renderer; не читает основной аккаунт и не запускает раннеров.

Облачный запуск: `.env.example` перечисляет окружение, `npm run build` + `npm start` запускает сервер. `Dockerfile` использует multi-stage build; runtime работает непривилегированным пользователем. В Railway подключается PostgreSQL через `DATABASE_URL`. Настоящие значения задавайте в secret settings, никогда не в публичных файлах, issue или чатах.

Версия хранится в `package.json`/`package-lock.json`. Тег `vX.Y.Z` запускает `.github/workflows/release.yml`: tests → Mac/Windows UI/native checks → installers → packaged smoke → GitHub prerelease + SHA256SUMS. Сам этот workflow **не деплоит Railway**. Публикация source/release и деплой coordinator — отдельные операции; делайте их после проверки и с разрешением владельца проекта.

Public repository пока `UNLICENSED`: публичность не предоставляет открытую лицензию. Не переносите реальные токены, настройки, рабочие папки, диагностические выводы и переписку команды в fixtures или документацию. В PR приложите описание, тесты, совместимость/миграцию и скриншоты только с синтетическими данными.
